Speed is the easy number to win, and on its own it proves nothing: a converter
that emits garbage quickly is worthless. So there are two halves here. The first
is timing. The second is a 130-document fidelity benchmark scored against
docling's ground truth, which is the number that decides whether the output is
worth having.

Every figure on this page comes from `bench/README.md` in the repo.

```sh
./bench/run.sh                             # speed, memory, coverage — needs uv, hyperfine and Go
./bench/run-quality.sh /path/to/docling    # quality — needs a docling checkout
```

## Environment

| | |
|---|---|
| Machine | Apple M5 Pro (darwin/arm64), macOS 25.4 |
| anymd | v0.3.0 for quality and the PDF section, Go 1.26. The speed and memory tables below were taken at v0.1.0 and are unchanged apart from PDF, which 0.3.0 rewrote and which is re-measured in [PDF, head to head](#pdf-head-to-head). |
| markitdown | 0.1.5, Python 3.12.13, `markitdown[all]` (pdfminer.six 20260107) |
| Corpus | the 31 files in markitdown's own test suite |

<Aside type="note" title="The benchmark is the default, offline build">
With `--llm` the wall clock is whatever the model takes, and the comparison
stops being about parsers.
</Aside>

### PDF used to be the exception — it is not any more

An earlier revision of the benchmark reported PDF at **45.69 ms, a 1.7× win**,
and explained it away as "both tools are dominated by the PDF parser itself".
That explanation was wrong twice over, and it is worth writing down why, because
it is the shape of mistake a benchmark exists to catch.

It named the wrong engine: anymd has never used pdfium. It parses PDFs with
`ledongthuc/pdf`, a fork of Russ Cox's `rsc.io/pdf`, now vendored as
`internal/pdf`. And it treated the cost as inherent when it was self-inflicted.
That library ships with no cache for resolved indirect objects — its own doc
comment says "the library makes no attempt at efficiency; a value cache
maintained in the Reader would probably help significantly" — while
`Page.Content()` asks for a glyph's width once per glyph, and each of those asks
re-reads and re-lexes the font's `/Widths` array from the file bytes. Laying out
a page was `O(glyphs × len(Widths))` trips through the lexer: for a 93 KB
document, **1,565,898 allocations and 75 MB**.

Adding the cache upstream describes is ~10 lines and leaves output
byte-identical on all seven corpus PDFs:

| file | before | after | |
|---|---:|---:|---:|
| test.pdf | 43.77 ms | 2.60 ms | **16.8×** |
| REPAIR-2022-INV-001_multipage.pdf | 13.34 ms | 1.34 ms | **10.0×** |
| RECEIPT-2024-TXN-98765_retail_purchase.pdf | 0.90 ms | 0.51 ms | 1.8× |
| movie-theater-booking-2024.pdf | 0.50 ms | 0.46 ms | — |
| SPARSE-2024-INV-1234_borderless_table.pdf | 0.48 ms | 0.44 ms | — |
| masterformat_partial_numbering.pdf | 0.12 ms | 0.11 ms | — |

The win tracks embedded fonts, not page count: documents with subset fonts and
large `/Widths` arrays were paying the quadratic, and documents drawing text in
a base-14 font never were. `BenchmarkConvertPdf` fell from 42.6 ms /
1,565,898 allocs / 75 MB to 2.59 ms / 16,605 allocs / 2.2 MB.

For the record, the parser choice is still real and still costs something.
pdfium extracts better than anymd does on hard layouts. It is also a C library,
and anymd's whole proposition is one static `CGO_ENABLED=0` binary, so it is not
free to adopt.

## PDF, head to head

PDF is the format most people arrive with, and it is the one where the two tools
are least alike. markitdown's PDF path is pdfminer.six text extraction: it
returns the prose and nothing else. anymd 0.3.0 recovers structure from the page
geometry. The difference is not a matter of a few percent on a similarity score,
so here is the blunt version — the same paper, both tools, counted:

| on `2206.01062.pdf` (the DocLayNet paper, 9 pages) | anymd | markitdown |
|---|---:|---:|
| headings emitted | **30** | 0 |
| table rows emitted | **68** | 0 |

Zero is not a rounding difference. A PDF converted by markitdown arrives at the
other end as one undifferentiated run of text: the section a passage came from,
and the table it was a cell of, are gone, and nothing downstream can put them
back. That matters most for the thing both tools are usually feeding — a
retrieval index, where the heading is what makes a chunk findable.

### Fidelity

The 15 PDFs of the docling corpus, scored the same way as everything else on
this page. The third column is anymd v0.1.0, when this page reported PDF tables
and headings as anymd's **largest remaining gap**:

| metric | anymd 0.3.0 | markitdown 0.1.5 | anymd v0.1.0 |
|---|---:|---:|---:|
| content | **0.94** | 0.90 | 0.87 |
| order | **0.83** | 0.74 | 0.77 |
| tables | **0.69** | 0.56 | 0.43 |
| headings | **0.59** | 0.20 | 0.14 |
| lists | **0.47** | 0.42 | 0.44 |

anymd now leads every PDF metric. Headings went from losing 0.14 to 0.20 to
winning 0.59 to 0.20, and tables from 0.43 to 0.69, which is the gap that page
called a missing feature rather than a tuning problem. `lists` is the honest
weak spot: 0.47 against 0.42 is a win by a nose, and several corpus PDFs still
score 0.00 on it.

### Speed

hyperfine, 8 runs after 2 warm-ups, stdout discarded, CLI end to end — so
markitdown's ~300 ms of interpreter start is included, because a script pays it
on every file.

| file | anymd | anymd `--no-images` | markitdown | speedup |
|---|---:|---:|---:|---:|
| normal_4pages.pdf | 33 ms | 26 ms | 679 ms | **21×** |
| redp5110_sampled.pdf | 36 ms | 29 ms | 1063 ms | **30×** |
| 2206.01062.pdf | 49 ms | 42 ms | 1532 ms | **31×** |

Structure recovery is not what costs the time: the extra work over
`--no-images` is 7 ms, and that is base64, not layout analysis.

### The one number that goes the other way

anymd's default PDF output is **much larger**, because 0.3.0 inlines figures as
base64 `data:` URIs:

| `2206.01062.pdf` output | bytes |
|---|---:|
| anymd, default | 960,241 |
| markitdown | 59,254 |
| anymd `--no-images` | **43,355** |

Sixteen times markitdown's output, and the figures are the whole of the
difference — with `--no-images` anymd is *smaller* than markitdown while
carrying 30 headings and 68 table rows it does not have. If the destination is a
context window, pass `--no-images`; if it is an archive that has to survive the
source file moving, keep them.

<Aside type="caution" title="Where markitdown still wins on PDF">
Presentations exported to PDF. On `odf_presentation_01.odp.pdf` and
`odf_presentation_02.odp.pdf` anymd scores content **0.04** and **0.06** against
markitdown's 0.94: it shatters the slide into single glyphs (`T`, `a r r`,
`l`, `u u`) and loses the title, where markitdown recovers the table. This is
not a 0.3.0 regression — v0.2.0 produces the same output — and it is an open
bug, not a trade-off. It is also what drags the `odf` row of the main results
table down, since those files route through the PDF converter.
</Aside>

## Coverage — the number that is easy to report dishonestly

A naive count says markitdown converts **30/31** files and anymd **26/31**. That
comparison is wrong, because exit code 0 is not the same as output.

Counting files that produce **substantive output (>200 bytes)**:

| | anymd | markitdown |
|---|---:|---:|
| substantive conversions | **19/31** | **19/31** |

Dead even. The five files anymd refuses break down as:

| file | anymd | markitdown |
|---|---|---|
| scanned medical PDF | `ErrNoTextLayer` (exit 1) | **0 bytes, exit 0** |
| test.jpg, test_llm.jpg | 131 / 60 bytes of EXIF | **0 bytes, exit 0** |
| test.mp3/.m4a/.wav | error (exit 1) | 29-byte transcript |
| random.bin | error | error |

Two things worth being precise about:

1. **markitdown genuinely transcribes audio.** It does it by sending the audio
   to a remote speech-recognition service, which is exactly the kind of
   convert-time network call anymd deliberately does not make by default.
   Different trade-off, not a defect on either side. anymd converts these with
   [`--llm-transcribe`](/anymd/llm/), which takes corpus coverage to 27 of 31.
2. **On the scanned PDF and both images, markitdown returns an empty string and
   exit 0.** For an ingestion pipeline that is the worst outcome: silently
   indexing nothing is indistinguishable from a document that genuinely had no
   text. anymd returns `ErrNoTextLayer` so a caller can route the file to OCR.

## Quality — fidelity, not byte counts

The corpus is [docling](https://github.com/docling-project/docling)'s test suite
— 130 in-scope documents shipped as (source, expected markdown) pairs under
`tests/data/<format>/{sources,groundtruth}`. Two things make it worth borrowing:
the pairs are machine-matchable, and the files are named for the feature they
exercise (`docx_lists.docx`, `xlsx_07_gap_tolerance_.xlsx`), so a low score
names the broken feature instead of merely asserting one exists.

<Aside type="note" title="docling is the target, not a contestant">
Its ground truth is its own frozen output, so it would score 1.00 by
construction and reporting that would be meaningless. It is not run. The
head-to-head is anymd vs markitdown, both of which are third parties to that
ground truth.
</Aside>

Scoring is style-insensitive on purpose. `| --- |` against `| - |`, `#` against
`##`, `<!-- image -->` against nothing — those are conventions, not defects, and
are normalized away before anything is compared.

### The metrics

| | what it catches |
|---|---|
| **content** | token F1, order-insensitive — dropped and invented content |
| **order** | token F1, order-**sensitive** — scrambled reading order |
| **tables** | each ground-truth table matched to its best candidate, scored on cell content |
| **headings** / **lists** | fraction of ground-truth items that survive |

**Content and order are a pair, and the gap between them is the point.** A
two-column PDF read straight down the page keeps every token, so content stays
high while order collapses. That gap separates a reading-order defect from a
content-loss defect, which no single similarity score can do.

`declined` counts explicit refusals (nonzero exit), which are withheld from the
averages. A tool that fails loudly hands the caller something actionable, and
scoring that 0.00 would punish the exact behaviour the coverage section argues
for. Exit-0-with-empty-output is *not* withheld — that is the silent failure,
and it scores 0 like any other miss.

order 0.91 → 0.92, content 0.92 → 0.93. It is the only change between this table
and the v0.1.0 one, which is a useful property of a benchmark that spans
formats: a PDF rewrite is not supposed to move `csv`, and it did not.

### Where anymd still loses

Two places now that PDF has been dealt with, and the first is much the larger:

- **`odf`** — content 0.64 against markitdown's 0.94, tables 0.31 against 0.38.
  These route through the PDF converter, and two files account for nearly all of
  it: `odf_presentation_01.odp.pdf` and `odf_presentation_02.odp.pdf` score
  content **0.04** and **0.06**, because a presentation exported to PDF comes
  apart into single glyphs. See the caution in
  [PDF, head to head](#pdf-head-to-head) — it is a bug, it predates 0.3.0, and
  it is now the largest remaining gap on this benchmark.
- **`pptx` content and order** — 0.79 against 0.82 and 0.78 against 0.82, while
  anymd wins tables, headings and lists on the same files. The losses are
  `powerpoint_with_image.pptx` (0.47) and `powerpoint_malformed_pictures.pptx`
  (0.68), so this is about text anymd does not reach inside picture shapes, not
  about the outline work 0.3.0 added — which took pptx lists from 0.56 to
  1.00.

### What the benchmark found on its first run

A quality benchmark earns its keep by naming bugs, not by producing a number.
These are the ones it found first. **All of them have since been fixed** — the
table is kept because it is the evidence that the benchmark works, and the
scores above are what the fixes produced.

| file | score | defect |
|---|---|---|
| `drawingml.docx` | content **0.08** | 13 bytes emitted — DrawingML canvas text and embedded chart data dropped entirely |
| `textbox.docx` | content **0.13** | Word text boxes (`w:txbxContent`) not extracted |
| `docx_rich_tables_01.docx` | tables **0.00** | rich table cells lost |
| `2203.01017v2.pdf` | content 0.82, order **0.50** | two-column arXiv paper: nearly all the text, half the order |
| `2206.01062.pdf` | content 0.71, order **0.47** | same defect |
| `table_mislabeled_as_picture.pdf` | content 0.97, order **0.49** | the textbook case — the content is *there*, the sequence is wrong |
| `xlsx_07_gap_tolerance_.xlsx` | tables **0.11** | one table dumped per sheet; separate logical tables not split on blank-row gaps |
| `hyperlink_02.html` | content 0.40 | link handling |

The three PDF rows were one bug, not three. `pdfPageText` ordered glyphs by `Y`
descending then `X` ascending, which on a two-column page interleaved the
columns line by line. A recursive XY-cut took PDF order 0.70 to 0.77, past
markitdown's 0.74, with content unchanged on all 15 files.

The two `docx` rows are the more serious pair. A scrambled PDF is visibly
degraded; a dropped text box is a document that silently converts to almost
nothing at exit 0 — which is the failure mode this project criticises markitdown
for elsewhere.

`table_misidentified_as_form.pdf` is the single declined file — a scanned PDF
with no text layer, refused with `ErrNoTextLayer`. The vision-model path handles
it, but is opt-in and unconfigured in this run, which is why the refusal still
stands.

### What this still does not measure

The ground truth is docling's output, so "quality" here means agreement with
docling. Where docling is itself wrong, matching it scores well — two of the
corpus filenames (`table_misidentified_as_form`,
`table_mislabeled_as_picture`) are docling's own record of getting a page wrong.
It also says nothing about formats docling ships no pairs for: rss, msg, zip,
ipynb, and images.
